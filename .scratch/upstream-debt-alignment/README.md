## Problem Statement

PowerI 在 `poweri/` 下持有一批**替换件**——它们整体替换上游同名组件，因此不随上游合并自动更新。合并上游时，`lib/`、`app/api/`、`hooks/` 自动全量跟随（当前 desktop 对 `upstream/main` 是 behind 0），但上游对替换件对照文件的改动**一条都不会进来**。

这造成三个用户可感知的后果：

1. **上游已修好的缺陷在 PowerI 上还在。** 用户遇到滚动位置丢失、草稿被清、SSE 重连后 shell 输出消失、扩展对话框标题被截断、两位数字号被裁切这类问题，在上游早已修复，在 PowerI 上照旧。
2. **上游新增的能力在 PowerI 上没有入口。** 会话搜索、CSV/TSV 表格预览、大文件分页、工作区终端标签、Git-ignored 文件开关、整项目删除会话——上游有，PowerI 没有。
3. **发布版本无法解释"改了这么多为什么界面没变"。** 0.2.12 相对 0.2.11 累计 739 个提交，绝大多数落在基础层（后端能力），界面无感。用户发出「界面还是一样啊，上游的修改都没有融合进来？」的疑问，是这条链路的直接症状。

更糟的是，这个问题此前**不可见**：登记表里 85 处未过账条目的理由字段是同一个占位符 `上游修复，替换件未同步（基线停在 0.9.0），需逐条评估是否补入`。占位符让审计持续通过（`pending` 不阻断 CI），也让任何人无法判断哪些真的没做、哪些其实做了。2026-10-23 的实测数据：85 处占位符里，真正已落地的只有 11 处（13%）。

## Solution

把「上游欠账」从一句笼统的免责声明，变成一套**可逐条关闭、可机器验证、可排期**的工作流：

1. **每条欠账有唯一身份和证据。** 一条上游提交 ↔ 一个替换件，附"上游新增行 N/M 命中"的落地证据与"仍缺哪一行"的具体缺口。占位符归零。
2. **每条欠账有明确归属。** 六类之一：已过账 / 刻意不做 / 功能缺失 / 缺陷修复 / 性能 / 细节打磨。前三类是事实判定，后三类是待排期的工作量。
3. **对齐工作有统一验收。** 不靠人眼比对，而靠三个已有测试缝 + 审计脚本 + CI，任何一条欠账关闭都必须留下可复核的记录。
4. **对齐进度可见。** 按替换件、按可感知度两个维度给出剩余量，让"下一步做哪块"由数据决定而不是凭感觉。

用户最终得到的是：**PowerI 界面上的每个组件，与上游同一组件的差异都是经过判断的，而不是被遗忘的。**

## User Stories

## Implementation Decisions

### 术语（沿用仓库既有词汇，不另造）

- **替换件（replacement）**：`poweri/` 下整体替换上游同名组件的文件。当前 12 个登记项。
- **对照文件（upstream counterpart）**：替换件所替换的上游文件，是审计的比较基准。
- **watermark**：上游提交水位，其之前对该对照文件的改动均已过账。只能经 `ack --watermark` 推进。
- **过账（account for）**：把一条上游提交处置为 `ported`／`waived`／`pending` 三者之一。
- **落地证据（landing evidence）**：该提交在对照文件里的新增行，在替换件中被逐行命中的比例。口径见 Testing Decisions。
- **可感知度（perceivability）**：把未处置条目分成「功能缺失／缺陷修复／性能／细节打磨／已过账／刻意不做」六类，用于排期。

### 1. 账目模型：三态处置 + 一个禁止项

每条上游提交对某个替换件的处置必须是 `ported`（已移植）、`waived`（刻意不做）、`pending`（待办）之一。新增硬约束：**`pending` 的理由必须包含可核对的具体缺口**（未命中的上游新增行、或缺失的具名标识符）。禁止再出现"需逐条评估""基线停在 0.9.0"这类不指向任何具体差异的措辞。

理由：当前 85 处占位符的根因不是懒，而是**审计脚本允许一个不携带信息的理由通过**。约束必须落在数据模型上，靠人自觉无效。

### 2. 判定算法：逐行落地检测，替代词频覆盖率

旧做法（本次已废弃）：统计上游新增行里的标识符，看替换件里出现多少。问题：公共标识符（`useState`、`background`、`item`）会把覆盖率虚抬到 40–70%，导致"看起来移植了一半"的假象。

新做法（本次已采用，写入登记表理由）：

1. 取区间 `watermark..upstream/main` 内、触及该对照文件的提交。
2. 对每个提交执行 `git show --unified=0 <sha> -- <对照文件>`，只取**该对照文件**的新增行（天然排除测试与文档，因为它们不在对照文件里）。
3. 丢弃长度 <12 字符的行与纯闭合符号行。
4. 归一化：去所有空白、去引号/逗号/分号。
5. 在替换件全文中逐行匹配，得命中率。
6. 阈值：≥60% 记 `ported`；20–59% 记 `pending` 且理由写"部分落地 N/M，仍缺 `<首个未命中行>`"；<20% 记 `pending` 且理由写"未落地 N/M，仍缺 `<首个未命中行>`"。

**这套算法必须是脚本的一部分，不是一次性分析。** 否则下一轮同步又会退回占位符。

### 3. 六类可感知度：用于排期，不写入 schema

可感知度是**派生视图**（由提交 subject 与命中率推出），不落进 `replacements.json`。理由：它是排期视角，会随人变化，写进登记表会造成第二种需要维护的真相。

当前分布（147 条 `pending`）：

| 可感知度 | 对话区 | 侧栏/会话列表 | 渲染/样式 | 文件面板 | 设置面板 | 合计 |
|---|---|---|---|---|---|---|

### 4. 过账工作流（每条欠账的固定步骤）

1. 读登记表里该条 `pending` 的缺口描述，定位要补的上游 diff。
2. 在上游已合并进基础层的 `lib/` 与叶子组件里找可复用的实现（**不重写**）。
3. 只改对应的 `poweri/` 替换件；需要改上游文件时停下——先过归属判定，第 1 层文件一律不动。
4. 复跑落地检测，确认命中率越过阈值。
5. `ack --port <sha> --reason "<落地在替换件的哪一处>"`，理由必须指向具体位置。
6. 若是接线类缺口（能力已在基础层但替换件没接），在既有接线测试里补一条断言。
7. `check` + typecheck + lint + test 全绿后提交。

### 5. 复用而非复制：叶子组件与基础层库

替换件应继续 import 上游叶子组件与 `lib/` 模块，不复制整文件。本轮清账已验证的可用叶子/库：`DelimitedTable`、`lib/delimited-table`、`lib/file-version`、`hooks/usePrismLanguages`、`lib/file-viewer-state`、`lib/initial-navigation`。

理由：复制会让下一条上游提交产生**两份欠账**（替换件要跟、副本也要跟）。`DelimitedTable` 直接 import 是本 spec 的成本模型基石——CSV 表格能力只有一行接线，不是 248 行重写。

### 6. 水位推进的时机

- 单条欠账关闭 → `ack --port`，不动 watermark。
- 一个替换件的 `pending` 全部处置完毕 → `ack --watermark <upstream/main>`，此时脚本会校验区间内无遗漏。
- 上游同步 PR → 必须先跑 `check`，逐项判定完再推进水位，然后加跑接线测试。

禁止手写 `watermark`：脚本已用 `watermarkProvenance` 拦住，手写会让审计区间变成空区间而永远通过。

## Testing Decisions

### 什么是好测试（本项目口径）

只测**外部可观察行为**，不测实现细节。具体到本 spec：

- ✅ 好的断言：`pending` 条目的理由必须包含一个具体的未命中行或具名标识符；某个能力在替换件里真的被 import 且被 props 传入；某个计算函数在给定输入下返回期望输出。
- ❌ 坏的断言：某个变量叫什么名字、某段 JSX 在第几行、内部函数被调用几次。上游改名就会误报。

### 测试缝：三个，零新增

经与用户确认，**不新增测试缝**。全部验收压在三个已有缝上：

**缝 1 —— 审计脚本（覆盖 147 条）**

`scripts/upstream-replacement-audit.mjs check` 是账目层的唯一缝。它已由 CI 每周一 + 每次 push 到 `poweri`/`desktop` 触发（`upstream-replacement-audit.yml`）。本 spec 要求：

- 新增 `pending` 理由的形态校验：理由必须匹配"含数字比值 + 含 `仍缺` 反引号片段"或"含具名标识符"，否则 `check` 失败。这是把"禁止占位符"从约定变成机器约束的唯一位置。
- 保留 `list --json` 供汇总视图消费。

**缝 2 —— 接线测试（覆盖跨组件缺口）**

`poweri/lib/replacement-wiring.test.mjs` 已存在，用途正是"上游能力已合并进基础层、但替换件没接线"这一缺口，写法是对源码做正则断言并交叉校验上游对照文件。样例：

```js
assert.match(shell, /pi-quote-selection-enabled/g);
assert.ok(count(upstreamShell, KEY) >= 2, "上游已不用该 key 则本测试与 PowerI 两侧均需同步修正");
```

所有"能力在 lib、入口在替换件"的欠账关闭时，都往这个文件加一条断言，不新建文件。

**缝 3 —— 纯函数单元测试（覆盖可抽离逻辑）**

上游已有 `lib/delimited-table.test.mjs`、`lib/file-version.test.mjs`。凡是新增的纯计算（分页区间、列宽测量、版本判重）都进这里可用的同一批目标，不自造平行实现。

### 不测什么

- 不新增 `/poweri` 路由的 e2e。现有 e2e 全部 goto 上游 `/`，扩展它属独立议题。
- 不为每个替换件新建 props 契约测试文件（用户已否决方案 B）。
- 不对 JSX 结构、样式数值、文案字符串做断言。

### 验收口径

一条欠账算关闭，需要同时满足：

1. 登记表里该条从 `pending` 变为 `ported`，理由指向具体落地位置。
2. 落地检测命中率越过阈值（≥60%）。
3. 若属接线类，缝 2 有对应断言；若属计算类，缝 3 有对应用例。
4. `check` + typecheck + lint + test 全绿。

## Out of Scope

- **上游文件本身的修改。** 第 1 层文件一律不动；需要上游配合的缺陷记 issue 等上游发版。
- **`poweri → desktop` 之外的任何数据流。** 本 spec 不改分支模型。
- **`SessionSidebar` 的架构性重写。** 它与上游相似度 19.3%，移植需要重做测量方案（虚拟滚动）与搜索面板接线，工作量远超其他替换件，单独开 spec。
- **终端集成（`TerminalPanel` + 终端标签）。** 涉及三处入口与新面板挂载，单独开 spec。
- **新增 e2e、视觉回归、截图比对。**
- **78 条 `waived` 条目的复核。** 本轮只清账不翻案；豁免理由是否仍成立，留到下一次同步时逐条确认。
- **Windows CI 的 79 项兼容债务。** 那是测试环境问题，与替换件过账无关（已在 `traps.md` 单独登记）。
- **发布节奏与版本号推进。**

### 一个必须承认的局限

落地检测是机器初判，**"该补 / 不补"仍是产品判断**。它能可靠回答"这一行在不在替换件里"，不能回答"这个功能 PowerI 要不要"。因此本 spec 把判定与决策显式分开：机器负责判定与证据，人（或实现代理，在有明确产品意图时）负责处置。任何 `ported`／`waived` 的写入都必须有理由，且理由要能让下一个人复核。
